• LangGraph là thư viện Python để dựng ứng dụng LLM có nhiều bước, rẽ nhánh, lặp, nhớ và dừng chờ người duyệt.
  • Mọi thứ được mô tả bằng một graph: State (dữ liệu chung) đi qua các Node (hàm Python) theo các Edge (mũi tên).
  • Agent thực chất chỉ là một graph có vòng lặp: LLM → gọi tool → LLM → … cho tới khi xong.

Bắt đầu từ thứ đã biết: gọi LLM một lần

Cách đơn giản nhất để dùng LLM: gửi câu hỏi, nhận câu trả lời.

tra_loi = llm.invoke("Đơn DH001 của mình tới đâu rồi?")

Với câu hỏi kiến thức chung thì ổn. Nhưng thử làm một trợ lý chăm sóc khách hàng cho shop thật, sẽ gặp ngay các vấn đề:

  • LLM không biết dữ liệu của mình. Muốn trả lời đơn DH001 tới đâu, nó phải gọi hàm tra cứu database, đọc kết quả, rồi mới trả lời. Đó là ít nhất hai lần gọi LLM với một bước chạy code ở giữa.
  • Không biết trước cần bao nhiêu bước. Có câu hỏi trả lời ngay được; có câu phải tra cứu đơn, rồi tra cứu chính sách đổi trả, rồi mới trả lời. Cần một vòng lặp để LLM tự quyết khi nào xong.
  • Phải nhớ cuộc trò chuyện. Khách hỏi tiếp “thế còn đơn kia?” — app phải biết “đơn kia” là gì.
  • Có việc không được để AI tự làm. Hoàn 350.000đ cho khách thì phải có nhân viên duyệt. App phải dừng lại, chờ người bấm nút, rồi chạy tiếp — có khi vài tiếng sau.
  • Người dùng muốn thấy tiến trình thay vì nhìn màn hình trắng 20 giây.

Tự viết bằng while và if thì được, nhưng code nhanh chóng rối: trạng thái nằm rải rác, khó lưu lại để chạy tiếp, khó debug. LangGraph cho một cách tổ chức chuẩn cho đúng những việc này.

Ý tưởng cốt lõi: phiếu công việc chuyền qua các bàn

Mình hình dung LangGraph như một văn phòng xử lý hồ sơ:

  • Có một phiếu công việc chuyền tay giữa các bàn. Trên phiếu ghi mọi thứ đã biết: câu hỏi của khách, kết quả tra cứu, câu trả lời nháp… Đó là State.
  • Mỗi bàn làm một việc: đọc phiếu, làm phần của mình, ghi thêm vào phiếu. Đó là Node — một hàm Python bình thường.
  • Mũi tên chỉ phiếu đi tiếp tới bàn nào. Có mũi tên cố định (“xong bàn A thì sang bàn B”), có mũi tên rẽ nhánh (“nếu là yêu cầu hoàn tiền thì sang bàn kế toán”). Đó là Edge.

Chỉ với ba khái niệm này mà dựng được từ chatbot đơn giản tới agent nhiều bước có người duyệt. Phần còn lại của khóa học là các cách dùng chúng.

Tự kiểm tra

Giải thích State, Node, Edge bằng lời của bạn.

State là dữ liệu chung đi qua graph (phiếu công việc); Node là một hàm đọc state và trả về phần cần cập nhật (một bàn làm việc); Edge là quy định node nào chạy tiếp theo (mũi tên).

Vì sao agent cần vòng lặp chứ không phải một chuỗi bước cố định?

llm.invoke() trả về chuỗi hay gì?

Một message (AIMessage). Lấy chữ bằng .text; ngoài ra còn thông tin như usage_metadata, tool_calls.

  1. Định nghĩa State bằng TypedDict.
  2. Viết các node: hàm nhận state, trả về dict chỉ chứa phần cần cập nhật.
  3. StateGraph(State) rồi add_node.
  4. add_edge nối từ START tới END.
  5. compile() rồi invoke().

Bài này chưa dùng LLM — cố ý. Mình muốn hiểu cơ chế graph trước bằng những hàm Python đơn giản nhất, chạy ra kết quả đoán trước được. Khi đã chắc cơ chế, thay một node bằng lời gọi LLM là chuyện nhỏ.

Mục tiêu: graph nhận tên khách, node thứ nhất tạo lời chào, node thứ hai thêm câu chúc.

Bước 1 — State: graph mang theo dữ liệu gì?

from typing import TypedDict

class State(TypedDict):
    ten: str
    loi_chao: str

TypedDict mô tả “phiếu công việc” có những ô nào và kiểu gì. Ở đây có hai ô: ten (tên khách) và loi_chao. Bên trong graph, state là một dict Python bình thường: {"ten": "Kiệt", "loi_chao": "..."}.

Bước 2 — Node: mỗi bàn làm một việc

from typing import TypedDict

class State(TypedDict):
    ten: str
    loi_chao: str

def chao(state: State):
    return {"loi_chao": f"Xin chào {state['ten']}!"}

def them_loi_chuc(state: State):
    return {"loi_chao": state["loi_chao"] + " Chúc một ngày tốt lành."}

Node là hàm Python thường. Điều quan trọng nhất của bài nằm ở đây: node không trả về cả state, chỉ trả về những ô nó muốn thay đổi. Node chao trả về {"loi_chao": ...} — ô ten không nhắc tới thì giữ nguyên. LangGraph tự gộp phần cập nhật vào state.

Node giống người ở một bàn: đọc cả phiếu, nhưng chỉ ghi vào ô của mình. Không cần chép lại cả phiếu.

Bước 3 — Tạo graph và thêm node

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    ten: str
    loi_chao: str

def chao(state: State):
    return {"loi_chao": f"Xin chào {state['ten']}!"}

def them_loi_chuc(state: State):
    return {"loi_chao": state["loi_chao"] + " Chúc một ngày tốt lành."}

builder = StateGraph(State)
builder.add_node("chao", chao)
builder.add_node("them_loi_chuc", them_loi_chuc)

StateGraph(State) tạo một “bản thiết kế” graph dùng state kiểu State. add_node("tên", hàm) đặt tên cho node — tên này dùng khi nối edge và hiện trong output.

Bước 4 — Nối edge

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    ten: str
    loi_chao: str

def chao(state: State):
    return {"loi_chao": f"Xin chào {state['ten']}!"}

def them_loi_chuc(state: State):
    return {"loi_chao": state["loi_chao"] + " Chúc một ngày tốt lành."}

builder = StateGraph(State)
builder.add_node("chao", chao)
builder.add_node("them_loi_chuc", them_loi_chuc)
builder.add_edge(START, "chao")
builder.add_edge("chao", "them_loi_chuc")
builder.add_edge("them_loi_chuc", END)

START và END là hai điểm đặc biệt có sẵn: điểm vào và điểm ra của graph. Ba dòng này đọc thành: bắt đầu → chao → them_loi_chuc → kết thúc.

Bước 5 — Compile và chạy

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    ten: str
    loi_chao: str

def chao(state: State):
    return {"loi_chao": f"Xin chào {state['ten']}!"}

def them_loi_chuc(state: State):
    return {"loi_chao": state["loi_chao"] + " Chúc một ngày tốt lành."}

builder = StateGraph(State)
builder.add_node("chao", chao)
builder.add_node("them_loi_chuc", them_loi_chuc)
builder.add_edge(START, "chao")
builder.add_edge("chao", "them_loi_chuc")
builder.add_edge("them_loi_chuc", END)
graph = builder.compile()

ket_qua = graph.invoke({"ten": "Kiệt"})
print(ket_qua)

compile() kiểm tra bản thiết kế (node nào không có đường đi tới, edge trỏ vào node không tồn tại…) và tạo ra graph chạy được. invoke(state_ban_dau) chạy từ đầu tới cuối và trả về state cuối cùng.

Mình chỉ truyền vào ten; ô loi_chao do hai node lần lượt điền.

stream: xem từng bước thay vì chỉ kết quả cuối

invoke chỉ cho kết quả cuối. Khi debug hay muốn hiện tiến trình cho người dùng, dùng stream — nó trả về từng mẩu ngay khi mỗi node chạy xong:

    print(buoc)

Mỗi dòng có dạng {tên_node: phần_cập_nhật} — đúng thứ node đó trả về. stream_mode="updates" là chế độ mình dùng nhiều nhất khi debug: nhìn vào là biết node nào đã chạy và nó ghi gì.

Tự kiểm tra

Node trả về {"loi_chao": "..."} thì ô ten trong state ra sao?

Giữ nguyên. Node chỉ cập nhật các key nó trả về; LangGraph gộp vào state hiện tại.

invoke và stream khác nhau thế nào?

invoke chạy hết rồi trả về state cuối; stream trả về từng mẩu (mặc định theo stream_mode) ngay khi mỗi bước xong.

Quên add_edge(START, ...) thì sao?

compile() báo lỗi vì graph không có điểm vào.

  • Mặc định, giá trị node trả về ghi đè ô cũ trong state.
  • Muốn nối thêm (danh sách tin nhắn, nhật ký), gắn reducer: Annotated[list, operator.add].
  • Chatbot/agent dùng sẵn MessagesState: có ô messages với reducer add_messages.

Vấn đề: dữ liệu biến mất

Giả sử mình muốn mỗi node ghi một dòng vào “nhật ký xử lý” để tiện debug. Viết như bài trước:

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    nhat_ky: list[str]

def a(state: State):
    return {"nhat_ky": ["a đã chạy"]}

def b(state: State):
    return {"nhat_ky": ["b đã chạy"]}

builder = StateGraph(State)
builder.add_node("a", a)
builder.add_node("b", b)
builder.add_edge(START, "a")
builder.add_edge("a", "b")
builder.add_edge("b", END)
graph = builder.compile()

print(graph.invoke({"nhat_ky": []}))
$ python reducer.py
{'nhat_ky': ['b đã chạy']}

Dòng của node a mất. Lý do: mặc định, giá trị node trả về thay thế giá trị cũ của ô đó. Node b trả về ["b đã chạy"] nên ô nhat_ky bị ghi đè thành đúng danh sách đó.

Có thể sửa bằng cách node tự đọc danh sách cũ rồi nối: state["nhat_ky"] + ["b đã chạy"]. Nhưng node nào cũng phải nhớ làm vậy — quên một chỗ là mất dữ liệu. LangGraph có cách gọn hơn.

Reducer: quy định cách gộp

Reducer là một hàm gắn vào một ô của state, quyết định “giá trị cũ + giá trị node trả về = giá trị mới” như thế nào. Gắn bằng Annotated:

import operator
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    nhat_ky: Annotated[list[str], operator.add]

# ... phần còn lại giữ nguyên

Đọc dòng 6: “ô nhat_ky là list[str], và khi gộp thì dùng operator.add”. Với list, operator.add(cu, moi) chính là cu + moi — nối hai danh sách.

$ python reducer.py
{'nhat_ky': ['a đã chạy', 'b đã chạy']}

Giờ mọi node chỉ cần trả về phần mới; việc nối do reducer lo. Các ô không có reducer (như loi_chao ở bài 3) vẫn ghi đè như cũ — đúng ý cho dữ liệu kiểu “giá trị hiện tại”.

MessagesState: state có sẵn cho chatbot

Vì gần như mọi chatbot/agent đều cần “một danh sách tin nhắn được nối thêm”, LangGraph có sẵn MessagesState — tương đương tự viết:

from typing import TypedDict, Annotated
from langgraph.graph.message import add_messages

class MessagesState(TypedDict):
    messages: Annotated[list, add_messages]

add_messages là reducer “thông minh” hơn operator.add: nối tin nhắn mới vào cuối, nhưng nếu tin nhắn mới có cùng id với tin cũ thì thay tin cũ — hữu ích khi về sau muốn sửa một tin nhắn. Nó cũng nhận cả dict kiểu {"role": "user", "content": "..."} và tự đổi sang message.

Thử một “bot nhại lại” — chưa có LLM, chỉ để xem state tin nhắn hoạt động:

from langchain_core.messages import HumanMessage, AIMessage
from langgraph.graph import StateGraph, START, END, MessagesState

def bot(state: MessagesState):
    cau_hoi = state["messages"][-1].content          # tin nhắn cuối cùng
    return {"messages": [AIMessage(content=f"Bạn vừa hỏi: {cau_hoi}")]}

builder = StateGraph(MessagesState)
builder.add_node("bot", bot)
builder.add_edge(START, "bot")
builder.add_edge("bot", END)
graph = builder.compile()

ket_qua = graph.invoke({"messages": [HumanMessage(content="Đơn DH001 tới đâu rồi?")]})
for m in ket_qua["messages"]:
    m.pretty_print()

Tự kiểm tra

Hai node cùng trả về {"nhat_ky": [...]}, ô nhat_ky không có reducer. Kết quả cuối là gì?

Chỉ còn giá trị của node chạy sau — ghi đè.

add_messages khác operator.add ở điểm nào?

add_messages thay tin nhắn có cùng id thay vì nối trùng, và tự đổi dict sang message. operator.add chỉ nối hai list.

Node trong chatbot nên trả về cả danh sách tin nhắn hay chỉ tin mới?

Chỉ tin mới. Trả về cả danh sách sẽ làm tin nhắn bị nhân đôi vì reducer nối thêm.

  • Node gọi LLM = một hàm: lấy state["messages"], gọi llm.invoke(...), trả về {"messages": [tra_loi]}.
  • System prompt ghép vào đầu danh sách lúc gọi, không cần lưu vào state.
  • Chữ chạy từng token: stream_mode="messages".

Từ bot nhại lại tới chatbot thật

Bài trước node bot chỉ nhại lại câu hỏi. Giờ thay ruột nó bằng một lời gọi Claude. Phần graph gần như không đổi — đúng như đã nói ở bài 1: LLM chỉ là một thứ được gọi bên trong node.

Hiện chữ chạy từng token

Model trả lời dài thì người dùng phải chờ vài giây nhìn màn hình trống. Với stream_mode="messages", LangGraph đưa ra từng mẩu chữ ngay khi model sinh:

for manh, meta in graph.stream({"messages": [HumanMessage("Gợi ý 3 cách phối áo sơ mi trắng")]},
                               stream_mode="messages"):
    print(manh.text, end="", flush=True)
  • Mỗi lần lặp nhận một cặp: manh (một mẩu tin nhắn, vài chữ) và meta (thông tin kèm theo, ví dụ meta["langgraph_node"] cho biết mẩu này từ node nào).
  • end="", flush=True — in nối tiếp trên cùng dòng và hiện ngay, tạo hiệu ứng chữ chạy.

Đây chính là cách các giao diện chat hiển thị câu trả lời. Khi gắn vào web (FastAPI…), mình gửi từng mẩu này về trình duyệt.

Tự kiểm tra

Vì sao không lưu SystemMessage vào state?

Không cần: ghép lúc gọi là đủ, state gọn hơn và sửa system prompt có hiệu lực ngay. Lưu vào state thì mỗi lượt có thể bị nhân đôi nếu ghép sai.

Model “nhớ” câu trước bằng cách nào?

Nó không nhớ gì giữa các lần gọi. Mình gửi lại toàn bộ danh sách tin nhắn mỗi lần, nên nó đọc được ngữ cảnh.

stream_mode="messages" trả về gì mỗi lần lặp?

Một cặp (mẩu tin nhắn, metadata) — mẩu chứa vài token vừa sinh.

  • add_conditional_edges("node_nguồn", ham_chon): chạy xong node nguồn thì gọi ham_chon(state), nó trả về tên node sẽ chạy tiếp.
  • Hàm chọn chỉ đọc state và quyết định, không sửa state.
  • Edge trỏ ngược về node trước = vòng lặp. Agent ở bài 7 chính là như vậy.

Vấn đề: không phải câu hỏi nào cũng đi cùng một đường

Trợ lý CSKH nhận đủ loại câu: hỏi đơn hàng, đòi hoàn tiền, hỏi linh tinh. Mỗi loại cần xử lý khác: hoàn tiền phải chuyển nhân viên, hỏi đơn phải tra cứu. Edge cố định (add_edge) chỉ đi một đường. Cần edge biết rẽ.

Viết từng bước

Bước 1 — State và node phân loại

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    cau_hoi: str
    loai: str
    tra_loi: str

def phan_loai(state: State):
    q = state["cau_hoi"].lower()
    if "hoàn tiền" in q:
        return {"loai": "hoan_tien"}
    if "đơn" in q:
        return {"loai": "don_hang"}
    return {"loai": "khac"}

Phân loại bằng từ khóa cho dễ hiểu và chạy không cần API key. Thực tế sẽ để LLM phân loại (xem cuối bài) — nhưng graph giữ nguyên.

Bước 2 — Ba node xử lý

def xu_ly_don_hang(state: State):
    return {"tra_loi": "Để mình tra cứu đơn hàng cho bạn."}

def xu_ly_hoan_tien(state: State):
    return {"tra_loi": "Yêu cầu hoàn tiền đã được chuyển cho nhân viên."}

def tra_loi_chung(state: State):
    return {"tra_loi": "Mình có thể giúp gì thêm cho bạn?"}

Bước 3 — Hàm chọn đường

def chon_nhanh(state: State) -> Literal["xu_ly_don_hang", "xu_ly_hoan_tien", "tra_loi_chung"]:
    if state["loai"] == "don_hang":
        return "xu_ly_don_hang"
    if state["loai"] == "hoan_tien":
        return "xu_ly_hoan_tien"
    return "tra_loi_chung"
  • Hàm chọn đọc state và trả về tên node (chuỗi). Nó không phải node — không được trả về dict cập nhật state.
  • Kiểu trả về Literal[...] liệt kê các đích có thể. Không bắt buộc để chạy, nhưng nhờ nó LangGraph biết vẽ đủ các nhánh trong sơ đồ.

Bước 4 — Nối graph

builder = StateGraph(State)
builder.add_node("phan_loai", phan_loai)
builder.add_node("xu_ly_don_hang", xu_ly_don_hang)
builder.add_node("xu_ly_hoan_tien", xu_ly_hoan_tien)
builder.add_node("tra_loi_chung", tra_loi_chung)
builder.add_edge(START, "phan_loai")
builder.add_conditional_edges("phan_loai", chon_nhanh)
for ten in ["xu_ly_don_hang", "xu_ly_hoan_tien", "tra_loi_chung"]:
    builder.add_edge(ten, END)
graph = builder.compile()

for cau_hoi in ["Đơn DH001 tới đâu rồi?", "Mình muốn hoàn tiền đơn DH002", "Shop mở cửa mấy giờ?"]:
    for buoc in graph.stream({"cau_hoi": cau_hoi}, stream_mode="updates"):
        print(buoc)
    print("---")

Vòng lặp: edge trỏ ngược

Hàm chọn có thể trả về tên một node đã chạy — graph quay lại đó. Ví dụ “thử lại tối đa 3 lần”:

def kiem_tra(state: State) -> Literal["goi_api", "__end__"]:
    if state["thanh_cong"] or state["so_lan"] >= 3:
        return END              # END chính là chuỗi "__end__"
    return "goi_api"            # quay lại thử tiếp

builder.add_conditional_edges("goi_api", kiem_tra)

Đây là mẩu ghép cuối cùng để hiểu agent: agent = node LLM + conditional edge “còn cần gọi tool không?” trỏ ngược về chính nó. Bài sau làm đúng như vậy.

Vòng lặp luôn cần điều kiện dừng. LangGraph có giới hạn số bước (recursion_limit) và báo GraphRecursionError khi vượt — nhưng ở bản 1.2 mặc định là khoảng 10.000 bước. Với agent gọi LLM, 10.000 bước là rất nhiều tiền API trước khi nó chịu dừng. Nên tự đặt thấp khi chạy: graph.invoke(dau_vao, {"recursion_limit": 25}). (Tài liệu cũ hay ghi mặc định là 25 — đã không còn đúng.)

Để LLM phân loại thay vì từ khóa

Từ khóa dễ sai (“không cần hoàn tiền đâu” cũng chứa “hoàn tiền”). Thực tế dùng LLM với structured output — bắt model trả về đúng một giá trị trong danh sách:

from pydantic import BaseModel

class PhanLoai(BaseModel):
    loai: Literal["don_hang", "hoan_tien", "khac"]

bo_phan_loai = llm.with_structured_output(PhanLoai)

def phan_loai(state: State):
    kq = bo_phan_loai.invoke(f"Phân loại câu hỏi của khách: {state['cau_hoi']}")
    return {"loai": kq.loai}

Chỉ node phan_loai đổi ruột; hàm chọn, các node khác và graph giữ nguyên. Đây là lợi ích của việc tách thành node: thay một mảnh không ảnh hưởng phần còn lại.

Tự kiểm tra

Hàm chọn trả về gì, và có được sửa state không?

Trả về tên node chạy tiếp (hoặc END). Không sửa state — việc đó là của node.

Vì sao nên khai kiểu Literal[...] cho hàm chọn?

Để LangGraph biết các đích có thể có, vẽ sơ đồ đúng và phát hiện sớm tên node sai.

Graph lặp mãi không dừng thì chuyện gì xảy ra?

Tới recursion_limit (mặc định khoảng 10.000 ở bản 1.2) thì dừng và báo GraphRecursionError. Nên tự đặt recursion_limit thấp, ví dụ 25, cho agent.

  • LLM không tự chạy code. Nó chỉ trả lời “hãy gọi hàm X với tham số Y”; code của mình chạy hàm rồi gửi kết quả lại.
  • @tool biến hàm Python thành tool — docstring chính là hướng dẫn cho LLM.
  • Agent = node LLM ⇄ ToolNode, nối bằng tools_condition: còn yêu cầu gọi tool thì sang tools, không thì kết thúc.
  • Vòng lặp này có tên chuẩn là ReAct (Reason + Act) — pattern agent phổ biến nhất. Bài 11 đặt nó cạnh các pattern khác.

Tool calling hoạt động thế nào

Bài 5 bot bịa thời gian giao hàng vì không có dữ liệu. Cách sửa: cho nó một “công cụ” tra cứu. Điều mình từng hiểu sai: LLM không gọi hàm Python được. Thứ thực sự diễn ra là một cuộc trao đổi:

  1. Mình gửi câu hỏi kèm danh sách tool (tên, mô tả, tham số).
  2. LLM đọc và trả về một AIMessage đặc biệt: không có chữ, chỉ có tool_calls — “hãy gọi tra_cuu_don_hang với ma_don="DH001"”.
  3. Code của mình chạy hàm thật, gói kết quả vào ToolMessage.
  4. Gửi lại cho LLM cả hội thoại + kết quả. LLM đọc và trả lời khách — hoặc xin gọi thêm tool khác.

Bước 3 → 4 có thể lặp nhiều lần. Đó là lý do cần vòng lặp, và LangGraph xử lý nó gọn gàng.

Bước 1 — Viết tool

from langchain_core.tools import tool

DON_HANG = {   # dữ liệu giả, thực tế là truy vấn database
    "DH001": {"trang_thai": "đang giao", "du_kien": "17/11"},
    "DH002": {"trang_thai": "đã giao", "du_kien": "12/11"},
}

@tool
def tra_cuu_don_hang(ma_don: str) -> dict:
    """Tra cứu trạng thái đơn hàng theo mã đơn, ví dụ DH001."""
    return DON_HANG.get(ma_don.upper(), {"loi": "không tìm thấy đơn"})

@tool đọc ba thứ từ hàm để tạo “bản mô tả” gửi cho LLM: tên hàm, docstring, tham số và kiểu. Kiểm tra xem nó hiểu gì:

>>> tra_cuu_don_hang.name
'tra_cuu_don_hang'
>>> tra_cuu_don_hang.description
'Tra cứu trạng thái đơn hàng theo mã đơn, ví dụ DH001.'
>>> tra_cuu_don_hang.args
{'ma_don': {'title': 'Ma Don', 'type': 'string'}}
>>> tra_cuu_don_hang.invoke({"ma_don": "DH001"})
{'trang_thai': 'đang giao', 'du_kien': '17/11'}

Docstring là prompt. LLM chọn tool nào và truyền tham số gì hoàn toàn dựa vào tên + docstring. Docstring mơ hồ (“xử lý đơn”) thì LLM gọi sai. Viết như đang dặn một nhân viên mới: tool làm gì, khi nào dùng, tham số trông như thế nào.

Bước 2 — Node agent: LLM biết có tool

from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, MessagesState

tools = [tra_cuu_don_hang]
llm = init_chat_model("anthropic:claude-opus-5-5")
llm_co_tool = llm.bind_tools(tools)

def agent(state: MessagesState):
    tra_loi = llm_co_tool.invoke(state["messages"])
    return {"messages": [tra_loi]}

bind_tools(tools) tạo một phiên bản model mà mỗi lần gọi sẽ gửi kèm mô tả các tool. Node agent giống hệt node chatbot ở bài 5 — chỉ khác là model giờ có thể trả về yêu cầu gọi tool.

Bước 3 — ToolNode và tools_condition

Hai mảnh dựng sẵn của LangGraph, mình không phải tự viết:

from langgraph.prebuilt import ToolNode, tools_condition

builder = StateGraph(MessagesState)
builder.add_node("agent", agent)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition)
builder.add_edge("tools", "agent")
graph = builder.compile()
  • ToolNode(tools) — node đọc tool_calls trong tin nhắn cuối, chạy đúng hàm với đúng tham số, trả về các ToolMessage. Lỗi trong tool được bắt và gửi lại cho LLM dưới dạng tin nhắn lỗi.
  • tools_condition — hàm chọn đường có sẵn: tin nhắn cuối có tool_calls → đi "tools"; không có → END. (Vì vậy node tool phải đặt tên đúng là "tools".)
  • add_edge("tools", "agent") — edge trỏ ngược: chạy tool xong quay lại cho LLM đọc kết quả. Đây là vòng lặp.

So với bài 6: chỉ là một conditional edge và một edge vòng lại. Không có gì mới — đó là cái hay khi đã nắm chắc nền.

Thí nghiệm: câu hỏi không cần tool

Hỏi “Chào shop!” và xem output: chỉ có một bước agent rồi kết thúc. LLM tự hiểu không cần tra cứu. Agent không đi một đường cố định — nó đi bao nhiêu vòng tùy câu hỏi.

Nhìn bên trong yêu cầu gọi tool

Nhớ đặt recursion_limit thấp cho agent (như 25 ở trên). Nếu tool liên tục trả lỗi, LLM có thể gọi đi gọi lại — mỗi vòng là một lần trả tiền API.

Tự kiểm tra

Ai thực sự chạy hàm tra_cuu_don_hang: LLM hay code của mình?

Code của mình (ToolNode). LLM chỉ trả về yêu cầu gọi hàm kèm tham số.

LLM dựa vào đâu để chọn tool và tham số?

Tên hàm, docstring và kiểu tham số mà @tool đọc ra và gửi kèm mỗi lần gọi.

Bỏ dòng add_edge("tools", "agent") thì sao?

Chạy tool xong không quay lại LLM, nên không có câu trả lời cuối cho khách — vòng lặp bị cắt.

  • Checkpointer lưu state sau mỗi bước. Gắn khi compile: compile(checkpointer=...).
  • Mỗi cuộc hội thoại là một thread, phân biệt bằng thread_id trong config.
  • Có checkpointer thì mỗi lượt chỉ cần gửi tin nhắn mới — lịch sử tự được nạp lại.

Vấn đề: mỗi lần invoke là một tờ giấy trắng

Tự kiểm tra

Có checkpointer rồi, mỗi lượt nên gửi gì vào invoke?

Chỉ tin nhắn mới, kèm config có thread_id. Lịch sử được nạp tự động.

Hai khách dùng chung một graph, làm sao không lẫn hội thoại?

Mỗi khách (mỗi cuộc trò chuyện) một thread_id riêng.

snap.next bằng () nghĩa là gì?

Thread đó đã chạy xong, không còn node nào chờ chạy.

  • interrupt(gia_tri) trong node: dừng graph, gửi gia_tri ra ngoài cho người xem.
  • Chạy tiếp bằng graph.invoke(Command(resume=quyet_dinh), config) — interrupt(...) trả về chính quyet_dinh.
  • Bắt buộc có checkpointer và thread_id (để nhớ đã dừng ở đâu).
  • Khi chạy tiếp, node bị dừng chạy lại từ dòng đầu.

Vấn đề: có việc không được để AI tự làm

Hoàn tiền, xóa dữ liệu, gửi email cho khách… sai một lần là mất tiền hoặc mất uy tín. Cần một bước: graph dừng lại, nhân viên xem đề xuất, bấm duyệt hoặc từ chối, rồi graph chạy tiếp đúng chỗ đó — có thể là vài phút hay vài giờ sau, ở một request HTTP khác. Mô hình này gọi là human-in-the-loop.

Ví dụ: duyệt hoàn tiền

Chưa cần LLM — một graph hai node: xin duyệt → hoàn tiền.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver

class State(TypedDict):
    ma_don: str
    so_tien: int
    ket_qua: str

def xin_duyet(state: State):
    print(">> node xin_duyet bắt đầu chạy")
    quyet_dinh = interrupt({"cau_hoi": f"Duyệt hoàn {state['so_tien']:,}đ cho đơn {state['ma_don']}?"})
    print(">> nhận quyết định:", quyet_dinh)
    return {"ket_qua": "da_duyet" if quyet_dinh == "dong_y" else "tu_choi"}

def hoan_tien(state: State):
    if state["ket_qua"] != "da_duyet":
        return {"ket_qua": "Không hoàn tiền."}
    return {"ket_qua": f"Đã hoàn {state['so_tien']:,}đ cho đơn {state['ma_don']}."}

builder = StateGraph(State)
builder.add_node("xin_duyet", xin_duyet)
builder.add_node("hoan_tien", hoan_tien)
builder.add_edge(START, "xin_duyet")
builder.add_edge("xin_duyet", "hoan_tien")
builder.add_edge("hoan_tien", END)
graph = builder.compile(checkpointer=InMemorySaver())

Dòng 13 là tâm điểm: interrupt(...) trông như một lời gọi hàm bình thường trả về quyet_dinh. Nhưng lần chạy đầu, nó không trả về — graph dừng ngay tại đó. Giá trị truyền vào interrupt (câu hỏi cần duyệt) được gửi ra ngoài.

Lần chạy 1: tới chỗ cần duyệt thì dừng

config = {"configurable": {"thread_id": "hoan-tien-01"}}

ket_qua = graph.invoke({"ma_don": "DH002", "so_tien": 350000}, config)
print(ket_qua)
print("đang dừng ở:", graph.get_state(config).next)

Tự kiểm tra

Vì sao interrupt bắt buộc phải có checkpointer?

Graph phải lưu state lúc dừng để lần resume (có thể ở request khác, lúc khác) nạp lại và chạy tiếp.

Resume thì node chứa interrupt chạy tiếp từ giữa hay từ đầu?

Từ đầu node. Lần này interrupt trả về giá trị resume thay vì dừng.

Một node gửi email thông báo rồi mới gọi interrupt xin duyệt. Lỗi gì sẽ xảy ra?

Email bị gửi hai lần: một lần lúc chạy tới interrupt, một lần khi node chạy lại lúc resume. Nên gửi sau interrupt hoặc tách node.

Bước 2 — Tool hoàn tiền có bước duyệt

from langgraph.types import interrupt

@tool
def hoan_tien(ma_don: str, so_tien: int, ly_do: str) -> str:
    """Hoàn tiền cho một đơn hàng. Chỉ dùng sau khi đã tra cứu đơn và số tiền
    không vượt quá tổng tiền của đơn. Cần nhân viên duyệt trước khi thực hiện."""
    quyet_dinh = interrupt({"hanh_dong": "hoan_tien", "ma_don": ma_don,
                            "so_tien": so_tien, "ly_do": ly_do})
    if quyet_dinh != "dong_y":
        return "Nhân viên đã từ chối yêu cầu hoàn tiền."
    # gọi API thanh toán thật ở đây — đặt SAU interrupt
    return f"Đã hoàn {so_tien:,}đ cho đơn {ma_don}."

Điểm hay: interrupt đặt được ngay trong tool. LLM cứ tự nhiên quyết định gọi hoan_tien; tới lúc thực thi thì graph dừng chờ người. Kết quả trả về cho LLM (“đã hoàn” hay “bị từ chối”) để nó báo lại khách cho đúng.

    "Bạn là trợ lý chăm sóc khách hàng của Kiệt Store. Trả lời ngắn gọn, lịch sự, bằng tiếng Việt. "
    "Luôn tra cứu đơn trước khi trả lời hay xử lý hoàn tiền. Không hứa điều gì ngoài dữ liệu tra được.")

def agent(state: MessagesState):
    return {"messages": [llm.invoke([SYSTEM] + state["messages"])]}

Bước 4 — Graph với vòng lặp và bộ nhớ

from langgraph.prebuilt import ToolNode, tools_condition
from langgraph.checkpoint.memory import InMemorySaver

builder = StateGraph(MessagesState)
builder.add_node("agent", agent)
builder.add_node("tools", ToolNode(tools))
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", tools_condition)
builder.add_edge("tools", "agent")

Giống hệt agent bài 7, thêm checkpointer của bài 8. Không có gì mới — đó là mục đích của bài này.

Bước 5 — Hàm chạy: hiện tiến trình và xử lý chờ duyệt

from langchain_core.messages import HumanMessage
from langgraph.types import Command

def chay(dau_vao, config):
    """Chạy graph, in từng bước. Trả về yêu cầu duyệt nếu graph dừng."""
    for buoc in graph.stream(dau_vao, config, stream_mode="updates"):
        for node, cap_nhat in buoc.items():
            if node == "__interrupt__":
                return cap_nhat[0].value               # graph đang chờ duyệt
            for m in cap_nhat["messages"]:
                if m.type == "ai" and m.tool_calls:
                    print(f"[{node}] gọi tool:", [(t["name"], t["args"]) for t in m.tool_calls])
                else:
                    print(f"[{node}] {m.type}: {m.text}")
    return None

if __name__ == "__main__":
    config = {"configurable": {"thread_id": "khach-02"}, "recursion_limit": 25}
    while True:
        cau_hoi = input("\nKhách: ")
        if cau_hoi == "q":
            break
        cho_duyet = chay({"messages": [HumanMessage(cau_hoi)]}, config)
        while cho_duyet:                                # có thể cần duyệt nhiều lần
            print("⏸  CẦN DUYỆT:", cho_duyet)
            quyet_dinh = input("Nhân viên (dong_y / tu_choi): ")
            cho_duyet = chay(Command(resume=quyet_dinh), config)
  • Khi graph dừng, stream trả về một mẩu có khóa __interrupt__ — mình bắt nó và trả về giá trị cần duyệt.
  • Vòng while cho_duyet: hỏi nhân viên, resume, và lặp nếu agent lại cần duyệt thêm việc khác.
  • Trong app thật, phần input() của nhân viên là một nút bấm trên trang quản trị, gửi request kèm thread_id và quyết định.

Workflow hay agent: ai cầm lái?

Mọi app LLM nằm đâu đó trên một dải:

Phân biệt rất đơn giản: nhìn vào chỗ chọn node tiếp theo. Nếu là hàm Python if/else do mình viết (như chon_nhanh ở bài 6) → workflow. Nếu là LLM tự quyết có gọi tool không, gọi tool nào (như tools_condition đọc tool_calls ở bài 7) → agent.

Mình từng nghĩ “dùng LLM” là “làm agent”. Không phải. Một workflow có thể gọi LLM ở mọi node (bài 5, bài 6 bản structured output) mà vẫn là workflow, vì đường đi do code quyết. Nhiều bài toán thực tế giải tốt nhất bằng workflow — rẻ hơn, ổn định hơn, dễ test hơn.

ReAct: tên của vòng lặp ở bài 7

ReAct = Reason + Act (suy luận + hành động), đặt tên theo một bài báo năm 2022. Ý tưởng gốc: cho LLM xen kẽ ba thứ — Thought (nghĩ xem cần làm gì), Action (gọi một công cụ), Observation (đọc kết quả) — lặp lại tới khi đủ thông tin để trả lời.

Hồi đó người ta phải ép LLM viết ra chữ “Thought: … Action: …” rồi tự cắt chuỗi để biết nó muốn gọi gì. Ngày nay model hỗ trợ tool calling sẵn (trả về tool_calls có cấu trúc), nên ReAct chỉ còn là đúng cái vòng lặp agent ⇄ tools ở bài 7. Khi tài liệu nói “ReAct agent”, cứ hiểu là: một LLM có tool, lặp tới khi không gọi tool nữa. Hàm create_agent ở Phần 2 dựng sẵn đúng một ReAct agent.

Dùng khi: không biết trước cần gọi tool nào, bao nhiêu lần. Không dùng khi: các bước đã biết trước — dùng chaining/routing, rẻ và ổn định hơn.

Plan-and-execute: lập kế hoạch trước, làm sau

ReAct quyết định từng bước một, “đi tới đâu tính tới đó”. Với việc dài nhiều bước, nó dễ đi lạc hoặc quên mục tiêu. Plan-and-execute tách làm hai vai:

  • Planner: đọc yêu cầu, viết ra danh sách bước.
  • Executor: làm lần lượt từng bước (mỗi bước có thể là một ReAct agent nhỏ có tool), ghi kết quả lại.

Lợi ích: kế hoạch hiện ra rõ ràng (cho người duyệt trước được!), executor có thể dùng model rẻ hơn, dễ biết đang ở bước nào.

Bước 1 — State và planner

import operator
from typing import TypedDict, Annotated
from pydantic import BaseModel
from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, END

llm = init_chat_model("anthropic:claude-opus-5-5")

class KeHoach(BaseModel):
    buoc: list[str]

class State(TypedDict):
    yeu_cau: str
    ke_hoach: list[str]                              # các bước CÒN LẠI
    da_lam: Annotated[list[str], operator.add]       # nhật ký, nối thêm (bài 4)

def lap_ke_hoach(state: State):
    kh = llm.with_structured_output(KeHoach).invoke(
        f"Lập kế hoạch tối đa 4 bước để xử lý yêu cầu: {state['yeu_cau']}")
    return {"ke_hoach": kh.buoc}

Structured output (bài 6) bắt LLM trả về đúng một danh sách bước, không phải đoạn văn tự do.

Bước 2 — Executor và vòng lặp

def thuc_hien(state: State):
    buoc = state["ke_hoach"][0]                       # lấy bước đầu tiên còn lại
    kq = llm.invoke(f"Yêu cầu: {state['yeu_cau']}\nĐã làm: {state['da_lam']}\nLàm bước: {buoc}")
    return {"ke_hoach": state["ke_hoach"][1:],        # bỏ bước vừa làm
            "da_lam": [f"{buoc} → {kq.text}"]}

def con_buoc(state: State):
    return "thuc_hien" if state["ke_hoach"] else END

builder = StateGraph(State)
builder.add_node("lap_ke_hoach", lap_ke_hoach)
builder.add_node("thuc_hien", thuc_hien)
builder.add_edge(START, "lap_ke_hoach")
builder.add_edge("lap_ke_hoach", "thuc_hien")
builder.add_conditional_edges("thuc_hien", con_buoc, ["thuc_hien", END])
graph = builder.compile()

Vòng lặp thuc_hien → thuc_hien chạy tới khi hết bước — đúng cơ chế vòng lặp của bài 6. Tham số thứ ba ["thuc_hien", END] liệt kê các đích có thể (thay cho kiểu Literal).

Reflection: viết – chấm – sửa

Người viết giỏi cũng tự đọc lại và sửa. Reflection (trong tài liệu của Anthropic gọi là evaluator–optimizer) cho một bước viết và một bước chấm theo tiêu chí rõ ràng, lặp tới khi đạt hoặc hết số vòng cho phép.

from typing import TypedDict
from pydantic import BaseModel
from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, END

llm = init_chat_model("anthropic:claude-opus-5-5")

class DanhGia(BaseModel):
    dat: bool
    gop_y: str

class State(TypedDict):
    de_bai: str
    ban_nhap: str
    gop_y: str
    so_vong: int

def viet(state: State):
    prompt = f"Viết tin nhắn cho khách: {state['de_bai']}"
    if state.get("gop_y"):
        prompt += f"\nBản trước: {state['ban_nhap']}\nSửa theo góp ý: {state['gop_y']}"
    return {"ban_nhap": llm.invoke(prompt).text, "so_vong": state.get("so_vong", 0) + 1}

def cham(state: State):
    dg = llm.with_structured_output(DanhGia).invoke(
        "Chấm tin nhắn CSKH theo tiêu chí: có mã đơn, có ngày dự kiến, lịch sự, có bù đắp.\n"
        + state["ban_nhap"])
    return {"gop_y": "" if dg.dat else dg.gop_y}

def du_tot_chua(state: State):
    if not state["gop_y"] or state["so_vong"] >= 3:   # đạt, hoặc đã sửa 3 lần
        return END
    return "viet"

Nối graph: START → viet → cham, rồi add_conditional_edges("cham", du_tot_chua, ["viet", END]).

Tự kiểm tra

Graph bài 6 (phân loại bằng LLM rồi rẽ nhánh) là workflow hay agent? Vì sao?

Workflow: LLM chỉ phân loại, còn đường đi do hàm chon_nhanh mình viết quyết định.

ReAct là gì, và trong LangGraph nó trông như thế nào?

Reason + Act: LLM lặp suy nghĩ → gọi tool → đọc kết quả tới khi trả lời được. Trong LangGraph là vòng agent ⇄ tools nối bằng tools_condition (bài 7), hoặc create_agent.

Khi nào chọn plan-and-execute thay vì ReAct?

Khi việc dài nhiều bước, cần thấy hoặc duyệt kế hoạch trước, hoặc muốn tách model lập kế hoạch và model thực thi.

Vì sao vòng reflection phải có giới hạn số vòng?

Bước chấm có thể không bao giờ hài lòng; không giới hạn thì lặp mãi và tốn tiền API.

  • create_agent (gói langchain) dựng sẵn đúng ReAct agent của bài 7: node model ⇄ node tools. Kết quả vẫn là graph LangGraph: invoke, stream, checkpointer, thread_id dùng y như cũ.
  • Thêm hành vi bằng middleware: móc chạy trước/sau khi gọi model, hoặc bọc quanh mỗi lần gọi model/tool.
  • HumanInTheLoopMiddleware thay cho việc tự gọi interrupt trong tool. Resume bằng Command(resume={"decisions": [...]}), mỗi decision là approve, edit, reject hoặc respond.

Bước 2 — Store: ghi nhớ sở thích của khách

Thêm một tool ghi_nho ghi vào Store theo mã khách, và một dynamic_prompt (bài create_agent) đọc Store đưa vào system prompt. Mã khách đi qua context, không để LLM tự điền.

import uuid
from dataclasses import dataclass
from langchain.agents import create_agent
from langchain.agents.middleware import dynamic_prompt, ModelRequest
from langchain.tools import tool, ToolRuntime
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore

@dataclass
class NguCanh:
    ma_khach: str

@tool
def ghi_nho(noi_dung: str, runtime: ToolRuntime[NguCanh]) -> str:
    """Ghi nhớ sở thích hoặc thông tin lâu dài của khách (giờ nhận hàng, địa chỉ...)."""
    runtime.store.put(("khach", runtime.context.ma_khach, "so_thich"), str(uuid.uuid4()), {"noi_dung": noi_dung})
    return "Đã ghi nhớ."

@dynamic_prompt
def prompt_co_tri_nho(request: ModelRequest) -> str:
    rt = request.runtime
    items = rt.store.search(("khach", rt.context.ma_khach, "so_thich"))
    nho = "\n".join(f"- {it.value['noi_dung']}" for it in items) or "(chưa có)"
    return f"Bạn là trợ lý CSKH của Kiệt Store.\nNhững điều đã biết về khách này:\n{nho}"

agent = create_agent("anthropic:claude-opus-5-5", tools=[tra_cuu_don_hang, ghi_nho],
                     middleware=[prompt_co_tri_nho], context_schema=NguCanh,
                     checkpointer=InMemorySaver(), store=InMemoryStore())

Tự kiểm tra

Khách dặn địa chỉ giao hàng ở cuộc trò chuyện hôm qua. Lưu bằng checkpointer hay Store?

Store. Checkpointer chỉ gắn với một thread; cuộc trò chuyện mới là thread mới nên không thấy. Store dùng chung cho mọi thread theo namespace.

Vì sao sau khi khởi động lại, Command(resume="dong_y") vẫn chạy tiếp được với PostgresSaver?

State lúc dừng (kể cả next và interrupt đang chờ) được lưu trong Postgres theo thread_id, nên tiến trình mới nạp lại được.

Vì sao mã khách đưa qua context thay vì để LLM truyền vào tool ghi_nho?

Để LLM không thể ghi/đọc nhầm hồ sơ khách khác. Context do code đưa vào, LLM không sửa được.

async def phat_su_kien(graph, dau_vao, config):
    dang_cho_duyet = False
    async for kieu, du_lieu in graph.astream(dau_vao, config, stream_mode=["messages", "updates"]):
        if kieu == "messages":
            manh, meta = du_lieu
            if isinstance(manh, AIMessageChunk) and manh.text and meta["langgraph_node"] == "agent":
                yield su_kien("chu", {"text": manh.text})
        elif "__interrupt__" in du_lieu:
            dang_cho_duyet = True
            yield su_kien("cho_duyet", du_lieu["__interrupt__"][0].value)
        elif "tools" in du_lieu:
            for m in du_lieu["tools"]["messages"]:
                yield su_kien("tool", {"ten": m.name, "ket_qua": m.text})
    if not dang_cho_duyet:                 # KHÔNG return giữa vòng lặp — xem cái bẫy
        yield su_kien("xong", {})
  • Nhiều chế độ thì mỗi phần tử là cặp (kieu, du_lieu). Với "messages", du_lieu lại là cặp (mẩu tin nhắn, metadata).
  • Phải lọc: chế độ messages trả cả ToolMessage nguyên khối từ node tools và các mẩu rỗng khi LLM gọi tool. Chỉ giữ AIMessageChunk có chữ, từ node agent (đọc meta["langgraph_node"]).
  • Dùng manh.text chứ không phải manh.content: với Claude, content có thể là list các block, .text luôn ra chuỗi.

Cách đọc:

  • Request chat đầu không có sự kiện chu: lượt này LLM chỉ gọi tool, chưa viết chữ nào. Nó kết thúc bằng cho_duyet, không có xong — giao diện hiện “đang chờ nhân viên duyệt”.
  • GET /threads cho trang nhân viên biết thread nào đang chờ, chờ gì. Đây là cùng next và interrupt đã học ở bài 8–9, chỉ đổi sang JSON.
  • Request duyệt chạy tiếp: kết quả tool rồi chữ chạy từng mẩu, cuối cùng xong. Gọi duyệt lần nữa thì 409 — không còn gì chờ.

Bản đầu mình viết return ngay sau yield su_kien("cho_duyet", ...) cho gọn. Request chat vẫn hiện đúng cho_duyet, nhưng GET /threads sau đó ra {"next":[],"so_tin_nhan":2,"cho_duyet":[]} và nút duyệt báo 409. Thoát khỏi vòng async for giữa chừng là hủy lần chạy trước khi nó kịp lưu xong chỗ dừng (mình thử thêm durability="sync" mà vẫn mất). Mình chạy thử 3 lần với Postgres: return sớm thì cả 3 lần mất interrupt; để vòng lặp tự kết thúc thì cả 3 lần còn đủ 4 tin nhắn và 1 interrupt. Quy tắc: đừng break/return giữa astream; dùng cờ như dang_cho_duyet.

Tự kiểm tra

Muốn hiện chữ chạy và đồng thời biết khi nào graph dừng chờ duyệt, dùng stream_mode nào?

stream_mode=["messages", "updates"]: messages cho từng mẩu chữ, updates cho kết quả node và khóa __interrupt__.

Vì sao /duyet phải kiểm tra snap.interrupts trước khi resume?

Command(resume=...) trên thread không chờ gì vẫn chạy: thread đã xong thì không làm gì, thread mới tinh thì graph chạy từ START với state rỗng. Kiểm tra trước và trả 409 tránh chạy nhầm.

Vì sao lọc meta["langgraph_node"] == "agent" ở chế độ messages?

Chế độ messages trả tin nhắn từ mọi node, gồm cả ToolMessage của node tools. Chỉ chữ của LLM ở node agent mới là chữ chạy cho khách.

import time, operator
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    ma_don: str
    ghi_chu: Annotated[list[str], operator.add]    # nhiều nhánh cùng ghi → cần reducer
    tra_loi: str

def kho(state: State):
    time.sleep(1.0); return {"ghi_chu": ["kho: còn hàng để đổi"]}
def van_chuyen(state: State):
    time.sleep(1.5); return {"ghi_chu": ["vận chuyển: giao ngày 12/11"]}
def thanh_toan(state: State):
    time.sleep(0.5); return {"ghi_chu": ["thanh toán: đã trả 350.000đ qua thẻ"]}
def tong_hop(state: State):
    return {"tra_loi": " | ".join(state["ghi_chu"])}

builder = StateGraph(State)
for ten, ham in [("kho", kho), ("van_chuyen", van_chuyen),
                 ("thanh_toan", thanh_toan), ("tong_hop", tong_hop)]:
    builder.add_node(ten, ham)
for ten in ["kho", "van_chuyen", "thanh_toan"]:
    builder.add_edge(START, ten)                                     # fan-out
builder.add_edge(["kho", "van_chuyen", "thanh_toan"], "tong_hop")   # fan-in: đợi đủ 3
builder.add_edge("tong_hop", END)
graph = builder.compile()

Bước 2 — Send: số nhánh theo dữ liệu

Shop muốn tóm tắt các đánh giá sản phẩm, số lượng mỗi ngày một khác. Không thể vẽ sẵn N node — dùng Send:

import operator
from typing import TypedDict, Annotated
from langchain.chat_models import init_chat_model
from langgraph.types import Send
from langgraph.graph import StateGraph, START, END

llm = init_chat_model("anthropic:claude-haiku-5-5")     # việc nhỏ, model rẻ

class State(TypedDict):
    danh_gia: list[str]
    y_chinh: Annotated[list[str], operator.add]
    bao_cao: str

class MotDanhGia(TypedDict):          # state riêng của MỖI nhánh
    stt: int
    noi_dung: str

def chia_viec(state: State):
    return [Send("tom_tat_mot", {"stt": i, "noi_dung": dg})
            for i, dg in enumerate(state["danh_gia"], 1)]

def tom_tat_mot(viec: MotDanhGia):
    y = llm.invoke(f"Tóm tắt trong 5 chữ: {viec['noi_dung']}").text
    return {"y_chinh": [f"#{viec['stt']}: {y}"]}

def gop(state: State):
    return {"bao_cao": "; ".join(state["y_chinh"])}

builder = StateGraph(State)
builder.add_node("tom_tat_mot", tom_tat_mot)
builder.add_node("gop", gop)
builder.add_conditional_edges(START, chia_viec, ["tom_tat_mot"])
builder.add_edge("tom_tat_mot", "gop")
builder.add_edge("gop", END)
graph = builder.compile()

Không có reducer thì một ô state chỉ nhận một giá trị mỗi bước; ba nhánh cùng ghi trong một bước thì LangGraph không biết giữ cái nào nên báo lỗi thay vì âm thầm ghi đè. Nhánh song song nên ghi vào ô riêng của mình, hoặc ô chung có reducer.

Tự kiểm tra

Ba node mất 1s, 1,5s và 0,5s chạy song song. Node gộp chạy sau bao lâu?

Khoảng 1,5s — bằng nhánh chậm nhất, vì cả ba cùng một superstep và node gộp đợi đủ.

Khi nào dùng Send thay vì nối edge cố định?

Khi số nhánh phụ thuộc dữ liệu lúc chạy (danh sách dài ngắn tùy lúc), hoặc mỗi nhánh cần dữ liệu đầu vào riêng.

Vì sao nên đặt max_concurrency khi mỗi nhánh gọi LLM?

Để không bắn quá nhiều request cùng lúc và bị rate limit (429) hoặc tốn chi phí đột biến.

from pydantic import BaseModel
from langchain.agents import create_agent

from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.types import Command

# tra_cuu_don_hang như bài 10; hoan_tien bản rút gọn (interrupt gửi ma_don, so_tien); tra_bao_hanh mới

agent_don_hang = create_agent("anthropic:claude-opus-5-5", tools=[tra_cuu_don_hang, hoan_tien],
    system_prompt="Bạn lo đơn hàng và hoàn tiền của Kiệt Store.", name="agent_don_hang")
agent_ky_thuat = create_agent("anthropic:claude-opus-5-5", tools=[tra_bao_hanh],
    system_prompt="Bạn lo bảo hành và lỗi kỹ thuật của Kiệt Store.", name="agent_ky_thuat")

    agent: Literal["agent_don_hang", "agent_ky_thuat"]
router = init_chat_model("anthropic:claude-haiku-5-5").with_structured_output(ChonAgent)

def dieu_phoi(state: MessagesState) -> Command[Literal["agent_don_hang", "agent_ky_thuat"]]:
    return Command(goto=router.invoke(state["messages"]).agent)

builder = StateGraph(MessagesState)
builder.add_node("dieu_phoi", dieu_phoi)
builder.add_node("agent_don_hang", agent_don_hang)      # graph đã compile làm node
builder.add_node("agent_ky_thuat", agent_ky_thuat)
builder.add_edge(START, "dieu_phoi")
builder.add_edge("agent_don_hang", END)
builder.add_edge("agent_ky_thuat", END)
graph = builder.compile(checkpointer=InMemorySaver())

tổng tin nhắn ở graph cha: 6

Cách đọc:

  • dieu_phoi -> None: node chỉ trả Command(goto), không cập nhật state.
  • Với subgraphs=True, mỗi dòng có thêm namespace: () là graph cha, ('agent_ky_thuat:<id>',) là bên trong agent con. Không bật thì chỉ thấy một dòng tổng agent_ky_thuat lúc nó chạy xong.
  • Câu hoàn tiền: interrupt trong tool hoan_tien nằm sâu trong agent con nhưng graph cha dừng, next chỉ vào node agent_don_hang. Resume ở graph cha, cùng thread_id, như bài 9.
  • Agent con trả lại cả tin nhắn câu hỏi, nhưng graph cha chỉ có 6 tin chứ không phải 7: reducer add_messages gộp theo id tin nhắn nên không nhân đôi.

Chung MessagesState nghĩa là agent kỹ thuật nhận mọi tin nhắn trước đó, kể cả các lần gọi tool hoàn tiền của agent đơn hàng ở lượt trước — tốn token và đôi khi làm nó bối rối. Cách khác hay dùng là gọi agent như một tool: supervisor là một create_agent có tool hoi_ky_thuat(cau_hoi), bên trong tool gọi agent_ky_thuat.invoke({"messages": [{"role": "user", "content": cau_hoi}]}) và trả về ["messages"][-1].text. Mình chạy thử: supervisor tự viết lại câu hỏi đầy đủ (“Tai nghe K2 mua 10 ngày, sạc không vào pin. Có được đổi không?”), agent con chỉ thấy đúng câu đó. Đổi lại, agent con không thấy ngữ cảnh khác — supervisor phải viết câu hỏi cho đủ.

Tự kiểm tra

Node trả Command(goto="agent_ky_thuat") khác gì so với conditional edge ở bài 6?

Cùng là routing. Command gộp quyết định và chuyển hướng vào trong node (có thể kèm update state); conditional edge tách việc chọn đường ra một hàm riêng gắn trên edge.

Tool hoan_tien gọi interrupt bên trong agent con. Resume ở đâu?

Ở graph cha: graph.invoke(Command(resume=...), config) với cùng thread_id. Agent con dùng checkpointer của graph cha.

Khi nào nên chia thành nhiều agent?

Khi một agent có quá nhiều tool bắt đầu chọn nhầm, hoặc các nghiệp vụ tách bạch cần prompt riêng. Nếu một agent với tool tốt đã đủ thì đừng chia: thêm agent là thêm lần gọi LLM, chậm và khó debug hơn.

Bước 1 — Graph nhận llm làm tham số

Sửa tro_ly_cskh.py của bài 10: thay vì tạo model ở cấp module, gói phần dựng graph vào một hàm.

def tao_graph(llm, checkpointer=None):
    llm_co_tool = llm.bind_tools(TOOLS)
    def agent(state: MessagesState):
        return {"messages": [llm_co_tool.invoke([SYSTEM] + state["messages"])]}
    builder = StateGraph(MessagesState)
    builder.add_node("agent", agent)
    builder.add_node("tools", ToolNode(TOOLS))
    # ... edge như bài 10 ...
    return builder.compile(checkpointer=checkpointer)

Code chạy thật gọi tao_graph(init_chat_model("anthropic:claude-opus-5-5"), PostgresSaver(...)); test truyền model giả.

Test với model giả kiểm tra được gì, không kiểm tra được gì?

Vì sao langgraph dev báo lỗi khi graph có checkpointer riêng?

Server LangGraph tự quản lý persistence cho mọi thread; checkpointer riêng sẽ bị bỏ qua khi deploy nên bản dev báo lỗi sớm để mình gỡ ra.
